# CodeAstra 架构与设计思路

## 1. 目标

CodeAstra 的核心目标不是简单调用大模型，而是产生可定位、可复核、可持续追问的代码审查证据。每条问题应关联文件、代码范围、证据、风险、建议和验证状态。

## 2. 审查流程

1. 用户登录并选择本地模型或 DeepSeek API。
2. 从粘贴内容、本地文件、版本对比或 GitLab 导入代码。
3. 创建归属于当前用户的审查会话。
4. 静态分析先发现确定性问题，模型补充语义与跨文件问题。
5. 服务层对结果进行范围、证据、重复项和覆盖率校验。
6. 前端通过 SSE 显示进度，并以文件和问题为中心展示结果。
7. 用户可处理问题、查看修订记录，或围绕具体文件/问题继续追问。

## 3. 分层

- `domain/`：审查、认证、模型协议等稳定领域对象和端口。
- `application/`：审查编排、模型选择、风险评分、用户管理和追问上下文。
- `infrastructure/`：SQLite、DeepSeek、本地模型、GitLab 等外部适配器。
- `api/`：FastAPI 路由、认证边界、CSRF、SSE 和请求/响应模型。
- `frontend/src/`：登录、账户管理、代码工作区、历史记录和集成界面。

## 4. 多模型策略

模型配置通过 profile 标识，而不是在业务代码中硬编码端点。审查创建后固定 profile 与具体模型，避免一次审查中途切换模型导致结果不可解释。DeepSeek Key 按浏览器账号空间隔离，本地 Qwen 通过 OpenAI 兼容接口接入。

## 5. 多用户与安全边界

- 服务端从认证会话得到 `user_id`，不信任客户端提交的 owner 字段。
- 审查、文件、历史、事件和追问均按 owner 范围访问。
- 管理员只有一个，普通用户不能访问管理接口。
- 写请求使用 CSRF 校验；新登录使旧会话失效。
- GitLab Token、DeepSeek Key、SSH Key 和生产数据库不进入源码仓库。

## 6. 追问上下文

追问应绑定审查、文件、问题或选区形成 `context_key`。历史只从相同 owner、review 和 context 读取，既让模型理解前文，又避免不同问题或不同用户之间串联上下文。

## 7. 部署边界

源码仓库不包含模型权重和生产配置。部署时分别启动模型服务与 CodeAstra 网关，并通过配置注入端点。生产环境需要 HTTPS、访问控制、备份、日志脱敏和明确的网络边界。
